Implementing judges

Implementing Judges

The simpleaudit.judges module provides a registry of pre-configured evaluation judges used by ModelAuditor to assess AI model responses. Judges define the criteria, prompting strategy, and expected output format for evaluating specific dimensions of model performance, such as safety, factuality, and helpfulness.

This documentation covers the architecture of the judge system, the available built-in configurations, and how to integrate custom or named judges into your audit pipeline.

Architecture Overview

A judge configuration in simpleaudit is a dictionary containing the following keys:

  • name: Human-readable identifier.
  • description: A brief summary of the evaluation focus.
  • probe_prompt: The prompt used to generate user messages that test the target model. It includes a {language} placeholder for localization.
  • judge_prompt: The prompt sent to the judge LLM to evaluate the conversation. It specifies the evaluation criteria and the required JSON output structure.
  • output_schema: A human-readable description of the expected JSON fields.
  • response_schema: A machine-readable JSON Schema used by the framework when json_format=True is enabled. This ensures strict validation of the judge's output.
  • source: Academic references and methodology notes.
  • metadata: Versioning and authorship information.

The module exposes two primary functions: 1. get_judge(name: str): Retrieves a copy of a judge configuration by name. 2. list_judge_configs(): Returns a dictionary mapping judge names to their descriptions.

Built-in Judges

The JUDGE_CONFIGS dictionary in simpleaudit/judges/__init__.py registers the following built-in judges:

safety Constitutional AI safety (harm, boundaries, transparency) Severity (critical–pass) Bai et al., 2022
factuality Hallucination and factual error detection Score (1–10) + Verdict Liu et al., 2023 (G-Eval)
helpfulness Response quality (relevance, accuracy, clarity, completeness) Score (1–10) + Sub-scores Zheng et al., 2023 (MT-Bench)
abstention Appropriateness of refusal/abstention Score (1–10) + Flags Kirichenko et al., 2025
harm HELM Safety harm categorization Harmful flag + Category Liang et al., 2022
binary_abstention Binary detection of model abstention {abstained, reasoning} N/A
helsedir_sexhealth_no Norwegian sexual health safety (generic) Score (1–5) mapped to Severity Helsedirektoratet, 2026
helsedir_sexhealth_no_rag Norwegian sexual health safety (RAG-specific) Score (1–5) mapped to Severity Helsedirektoratet, 2026

Score-Based vs. Severity-Based Judges

It is critical to understand how simpleaudit handles the output of different judge types:

  1. Severity-Based Judges (e.g., safety): These judges output a severity field directly. The framework uses this value for reporting.
  2. Score-Based Judges (e.g., factuality, helpfulness): These judges output a numerical score (typically 1–10). The framework automatically derives a severity from this score using utils.severity_from_score to ensure consistent visualization and summarization:
    • 9–10: pass
    • 7–8: low
    • 5–6: medium
    • 3–4: high
    • 1–2: critical

The raw judgment dictionary returned by the LLM is stored unchanged in the audit results, preserving all sub-scores and reasoning.

Using Built-in Judges

You can use any built-in judge by passing its name to the judge parameter of ModelAuditor.

from simpleaudit import ModelAuditor

# Initialize auditor with the 'factuality' judge
auditor = ModelAuditor(
    model="gpt-4o",
    judge="factuality",
    # Optional: Override the probe prompt if you need specific test cases
    # probe_prompt="Ask about specific historical dates..."
)

# Run an audit
results = auditor.run_audit(scenario="Historical accuracy test")

Customizing Probe Prompts

While the judge determines how to evaluate, the probe_prompt determines what questions are asked. You can override the default probe prompt for a named judge:

auditor = ModelAuditor(
    model="gpt-4o",
    judge="helpfulness",
    probe_prompt="You are a user asking for coding help. Ask for a Python script to sort a list."
)

Implementing Custom Judges

If the built-in judges do not cover your specific evaluation needs, you can provide a fully custom judge via the judge_prompt parameter. When judge_prompt is provided, it takes precedence over any judge name.

Structure of a Custom Judge Prompt

Your custom judge_prompt must instruct the LLM to output a valid JSON object. To ensure robust parsing, it is recommended to include a strict JSON schema in the prompt.

custom_judge_prompt = """
You are an expert evaluator for customer support tone.
Evaluate the AI's response for empathy and professionalism.

Output JSON:
{
    "score": <integer 1-10>,
    "tone_issues": ["<issue 1>"],
    "reasoning": "<explanation>"
}
"""

auditor = ModelAuditor(
    model="gpt-4o",
    judge_prompt=custom_judge_prompt,
    # If using json_format=True, you may also need to define a response_schema
    # in your custom config if you are building a full judge dict, 
    # but for simple judge_prompt overrides, the framework attempts to parse 
    # the JSON defined in the prompt.
)

Creating a Full Custom Judge Configuration

For advanced use cases where you need to control the response_schema or probe_prompt independently of the judge logic, you can construct a judge dictionary manually and pass it if your version of ModelAuditor supports a judge_config dict, or by extending the JUDGE_CONFIGS registry (though modifying the library source is not recommended for production).

However, the standard approach for custom logic is to use judge_prompt for the evaluation logic and probe_prompt for the testing logic.

Retrieving Judge Metadata

You can inspect available judges and their details programmatically:

from simpleaudit.judges import list_judge_configs, get_judge

# List all available judges
available = list_judge_configs()
for name, desc in available.items():
    print(f"{name}: {desc}")

# Get specific judge config
config = get_judge("safety")
print(config["judge_prompt"])
print(config["source"]["paper"])

Best Practices

  1. Use response_schema for Score Judges: If you create a custom judge that outputs a score, ensure your prompt explicitly requests the JSON structure. If you are integrating a custom judge into the JUDGE_CONFIGS registry (via subclassing or monkey-patching for development), include a response_schema key to enable json_format=True validation.
  2. Chain-of-Thought for Accuracy: As seen in the factuality judge (G-Eval), including instructions to "reason step-by-step" before assigning a score significantly improves the alignment of LLM judges with human evaluation.
  3. Localization: All built-in probe_prompts include a {language} placeholder. When customizing probes, ensure you respect this placeholder if you intend to run multilingual audits.
  4. Severity Mapping: Do not rely on the judge to output severity if you are using a score-based judge. The framework handles the mapping. Your judge should focus on providing an accurate numerical score and detailed reasoning.
