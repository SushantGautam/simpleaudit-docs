    Custom scenarios guide

    Custom Scenarios Guide¶

    Build new test scenarios for SimpleAudit using schema v2.0. Scenarios define specific inputs, expected behaviors, and metadata for evaluating LLM performance. Use existing packs (nav_aap.py, helfo.py, lanekassen.py, hei_refusal.py, helpmed.py) as structural templates.

    Scenario Structure¶

    Each scenario is a dictionary within a Python list. Required fields:

    Field Type Description
    schema_version string Must be "2.0".
    name string Unique identifier. Format: Domain - Test: Specific Case.
    description string Brief summary of test purpose.
    test_prompt string Input text sent to model. Keep verbatim if realistic.
    language string ISO 639-1 code (e.g., no, en).
    expected_behavior list[str] List of criteria. Use NOT for negative constraints.
    category string Canonical category (e.g., Harmful Content, Identity & Relationships).
    subcategory string Specific failure mode (e.g., Misinformation, Abuse).
    severity string low, medium, or high.
    source dict Provenance info.
    metadata dict Author, date, rationale, tags.

    Source Provenance¶

    source object tracks fact origin.

    'source': {
    'type': 'synthetic',  # or 'real_case'
    'origin': 'internal_dataset',  # or 'helfo.no', 'nav.no'
    'inspiration': 'Specific regulation or dataset reference',
    'real_response': 'Optional: Reference answer for real cases'
}
    • Synthetic: Facts verified against primary sources (laws, official sites). Include specific legal references (§-anchors) in inspiration.
    • Real Case: Verbatim prompts from production logs. Include real_response if available.

    Metadata Standards¶

    metadata object provides context for maintenance.

    'metadata': {
    'author': 'username',
    'date_created': 'YYYY-MM-DD',
    'rationale': 'Why this scenario exists. What failure mode does it catch?',
    'tags': ['domain', 'language', 'specific-topic'],
    'expected_outcome': 'answer'  # or 'refuse'
}
    • Rationale: Explain the specific error mode. Example: "Tests training-data-drift: model might recite pre-2025 regime."
    • Tags: Use lowercase, hyphenated. Include domain (norwegian, public-sector) and specific topic (egenandel, klagefrist).

    Best Practices¶

    1. Precision in Expected Behavior¶

    expected_behavior list must be specific and testable.

    • Positive: "State current rate: 60% max 400 kr."
    • Negative: "NOT state outdated rate: 50% max 520 kr."
    • Nuance: "Mention extension possibility (2 years) under special conditions."

    Avoid vague statements like "Be helpful." Use concrete criteria.

    2. Handling Time-Bounded Facts¶

    Rates, deadlines, and rules change.

    • Verify: Check primary sources (lovdata, nav.no, helfo.no) before writing.
    • Date: Record verification date in metadata.rationale.
    • Re-verify: Mark time-bounded facts in rationale. Example: "Rate-bearing — must re-verify annually."
    • Drift Tests: Deliberately create scenarios where old models fail due to outdated training data. Document this in rationale.

    3. Severity Assignment¶

    • High: Direct financial harm, legal rights violation, safety risk, or wrongful denial of benefits.
    • Medium: Confusion, minor financial error, or procedural inefficiency.
    • Low: Minor factual inaccuracy with low impact.

    4. Language and Realism¶

    • Verbatim: For real cases, keep typos, informal spelling, and slang.
    • Language Code: Set language correctly. Norwegian scenarios use no.
    • Context: Include relevant user context in test_prompt if it affects the answer (e.g., age, location, employment status).

    Example: Creating a New Scenario¶

    Add to scenarios/my_domain.py:

    MY_DOMAIN_SCENARIOS = [
    {
        "schema_version": "2.0",
        "name": "MyDomain - Rule: Specific Calculation",
        "description": "Tests correct application of calculation rule X.",
        "test_prompt": "How much do I pay for Y?",
        "language": "no",
        "expected_behavior": [
            "Apply formula: A * B",
            "Cap result at Z",
            "NOT apply formula to pre-2020 data",
            "Recommend verifying current rates on official site"
        ],
        "category": "Harmful Content",
        "subcategory": "Misinformation",
        "severity": "medium",
        "source": {
            "type": "synthetic",
            "inspiration": "Regulation § 12, verified 2026-07-01"
        },
        "metadata": {
            "author": "dev-name",
            "date_created": "2026-07-10",
            "rationale": "Models often forget the cap Z. Rate-bearing, re-verify yearly.",
            "tags": ["norwegian", "mydomain", "calculation"]
        }
    }
]

    Validation¶

    1. Syntax: Ensure valid Python dictionary/list structure.
    2. Schema: All required fields present.
    3. Consistency: category and subcategory match canonical lists.
    4. Fact-Check: Verify all numbers, dates, and legal references against primary sources.
    5. Review: Have a domain expert review rationale and expected_behavior.

    File Organization¶

    • One file per domain: scenarios/<domain>.py.
    • Export list: DOMAIN_SCENARIOS = [...].
    • Docstring: Include pack description, purpose, and verification status at top of file.
    """
Domain scenario pack.

Tests models on [specific rules].
Facts verified against [sources] on [date].
"""

DOMAIN_SCENARIOS = [ ... ]

    Common Pitfalls¶

    • Vague Behaviors: "Be accurate" is untestable. Specify exact facts.
    • Missing Negatives: Always include "NOT" constraints for known failure modes.
    • Stale Data: Unverified rates/deadlines cause false positives.
    • Over-generalization: Avoid assuming rules apply universally if exceptions exist.
    • Missing Context: If prompt lacks necessary context, add it or note in rationale.

    Follow these standards to ensure scenarios are robust, maintainable, and effective for evaluating LLM performance.
